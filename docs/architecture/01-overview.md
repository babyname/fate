# fate 架构总览

## 架构概述

fate 采用**模块化分层架构**，分为5个核心模块：

```
cmd（入口） → config（配置） → chronos（计算） → naming（推荐） → analysis（输出）
```

每个模块职责清晰，接口定义明确，依赖关系单向。

fate 是一个八字五行起名系统，采用模块化架构设计，分为入口层（cmd）、业务层（命名、分析）、数据层（chronos、八字）和配置层（config）。

---

## 模块划分

### 核心模块

| 模块 | 职责 | 核心功能 | 依赖 |
|-----|------|---------|------|
| **cmd** | 入口层 | CLI命令、起名交互 | config, chronos, naming, analysis |
| **config** | 配置层 | 配置加载、配置验证、配置管理 | 无 |
| **chronos** | 计算层 | 八字计算、五行喜忌分析、数据提供 | config, lunar-go |
| **naming** | 推荐层 | 名字筛选、名字评分、名字推荐 | config, chronos |
| **analysis** | 输出层 | 八字解析输出、名字解析输出、格式化 | config, chronos, naming |

### 模块职责详解

#### 1. cmd 模块（入口层）

**职责**：
- 提供CLI命令入口
- 提供起名交互入口
- 协调各模块工作流程

**核心功能**：
- `console`：交互式起名工具
- `character`：字表管理工具
- `dictctl`：字典工具
- `seeddb`：数据库种子数据
- `inspectdb`：数据库检查

**依赖**：
- config（配置管理）
- chronos（计算数据）
- naming（推荐名字）
- analysis（格式化输出）

---

#### 2. config 模块（配置层）

**职责**：
- 配置文件加载（YAML/JSON）
- 配置参数验证
- 配置参数管理
- 默认配置提供

**核心功能**：
- `LoadConfig()`：加载配置文件
- `ValidateConfig()`：验证配置参数
- `GetConfig()`：获取配置参数

**依赖**：无（独立模块）

---

#### 3. chronos 模块（计算层）

**职责**：
- 八字计算（年柱、月柱、日柱、时柱）
- 五行喜忌分析（喜用五行、忌神五行）
- 数据提供（为 naming 和 analysis 提供数据）
- lunar-go 桥接（适配器模式）

**核心功能**：
- `GetFateData()`：一次性返回所有数据
- `CalculateBazi()`：计算八字信息
- `CalculateWuxingXiji()`：计算五行喜忌信息

**依赖**：
- config（配置参数）
- lunar-go（农历计算库）

**关键特点**：
- 专为 fate 优化（简化输出、提高性能）
- 桥接 lunar-go（适配器模式隔离）
- 自己实现五行喜忌分析（lunar-go 不提供）

---

#### 4. naming 模块（推荐层）

**职责**：
- 名字筛选（根据五行喜忌筛选）
- 名字评分（综合评分：五行、笔画、音韵）
- 名字推荐（排序推荐最佳名字）
- 名字生成（组合规则）

**核心功能**：
- `FilterNames()`：筛选名字
- `RateNames()`：评分名字
- `RecommendNames()`：推荐名字

**依赖**：
- config（配置参数）
- chronos（八字数据、五行喜忌数据）

**关键特点**：
- 科学筛选（基于五行喜忌）
- 综合评分（多维度评分）
- 大数据库支持（5000-10000 个汉字）

---

#### 5. analysis 模块（输出层）

**职责**：
- 八字解析输出（格式化八字信息）
- 名字解析输出（格式化名字信息）
- 评分图表输出
- 周易卦象输出

**核心功能**：
- `FormatBaziOutput()`：格式化八字输出
- `FormatNameOutput()`：格式化名字输出
- `FormatOutput()`：通用格式化输出

**依赖**：
- config（配置参数）
- chronos（八字数据）
- naming（名字数据）

**关键特点**：
- 多格式支持（文本、JSON）
- 美名腾风格分析输出
- 评分图表展示

## 层次设计

### 分层架构

fate 采用**三层架构**：

```
┌─────────────────────────────────────┐
│      输出层（analysis）              │  ← 格式化输出
├─────────────────────────────────────┤
│      业务层（naming）                │  ← 推荐名字
├─────────────────────────────────────┤
│      数据层（chronos）               │  ← 计算数据
├─────────────────────────────────────┤
│      配置层（config）                │  ← 配置管理
├─────────────────────────────────────┤
│      入口层（cmd）                   │  ← 入口协调
└─────────────────────────────────────┘
```

### 层次职责

| 层次 | 职责 | 说明 |
|-----|------|------|
| **输出层** | 格式化输出 | 将数据格式化为用户可读的输出 |
| **业务层** | 推荐名字 | 根据数据进行业务逻辑处理 |
| **数据层** | 计算数据 | 提供核心数据（八字、五行喜忌） |
| **配置层** | 配置管理 | 管理配置参数 |
| **入口层** | 入口协调 | 协调各模块工作流程 |

### 层次依赖关系

**单向依赖**（上层依赖下层）：

```
cmd（入口层） → config, chronos, naming, analysis
analysis（输出层） → config, chronos, naming
naming（业务层） → config, chronos
chronos（数据层） → config
config（配置层） → 无
```

**依赖原则**：
- 上层依赖下层
- 下层不依赖上层
- 避免循环依赖
- 依赖关系清晰

## 架构模式

### 模块化模式

**特点**：
- 每个模块独立
- 模块职责清晰
- 模块接口明确
- 模块可替换

**优势**：
- 易于开发和维护
- 易于测试
- 易于扩展
- 易于替换

---

### 分层模式

**特点**：
- 层次职责清晰
- 层次依赖单向
- 层次接口明确
- 层次可替换

**优势**：
- 易于理解和维护
- 易于测试
- 易于扩展
- 易于替换

---

### 依赖注入模式

**特点**：
- 通过接口注入依赖
- 避免硬编码依赖
- 易于替换实现
- 易于测试

**示例**：

```go
// 定义接口
type ChronosInterface interface {
    GetFateData(input *FateInput) (*FateData, error)
}

// naming 模块通过接口依赖 chronos
type Naming struct {
    chronos ChronosInterface
    config  *Config
}

// 注入依赖
func NewNaming(chronos ChronosInterface, config *Config) *Naming {
    return &Naming{
        chronos: chronos,
        config:  config,
    }
}
```

**优势**：
- 易于替换实现（如替换 chronos 实现）
- 易于测试（如使用 mock chronos）
- 易于扩展（如添加新实现）

## 设计原则

### 单一职责原则（SRP）

**每个模块只有一个职责**：
- chronos：只负责计算数据
- naming：只负责推荐名字
- analysis：只负责格式化输出
- config：只负责配置管理
- cmd：只负责入口协调

---

### 接口隔离原则（ISP）

**每个模块提供最小接口**：
- chronos：只提供 `GetFateData()` 接口
- naming：只提供 `FilterNames()`, `RateNames()`, `RecommendNames()` 接口
- analysis：只提供 `FormatOutput()` 接口

---

### 依赖倒置原则（DIP）

**高层模块依赖抽象接口，不依赖具体实现**：
- naming 依赖 `ChronosInterface` 接口，不依赖 chronos 具体实现
- analysis 依赖 `ChronosInterface` 和 `NamingInterface` 接口

---

### 开放封闭原则（OCP）

**模块对扩展开放，对修改封闭**：
- 可以扩展模块功能（如添加新的输出格式）
- 不修改模块核心代码

---

## 架构优势

### 1. 模块化优势

**易于开发和维护**：
- 每个模块独立开发

- 模块接口明确，易于 mock

**易于扩展**：
- 添加新模块不影响现有模块
- 扩展模块功能不影响核心代码

**易于替换**：
- 模块可替换（如替换 chronos 实现）
- 模块可升级（如升级 lunar-go）

---

### 2. 分层优势

**易于理解和维护**：
- 层次职责清晰，易于理解
- 层次依赖单向，易于维护

**易于测试**：
- 每层独立测试
- 层次接口明确，易于 mock

**易于扩展**：
- 添加新层不影响现有层
- 扩展层功能不影响核心代码

---

### 3. 依赖注入优势

**易于替换**：
- 通过接口注入依赖，易于替换实现
- 测试时可使用 mock 实现

**易于测试**：
- 通过接口注入 mock 依赖
- 单元测试独立进行

---

### 4. 性能优势

**一次性数据计算**：
- chronos 的 `GetFateData()` 一次性返回所有数据
- 减少多次调用的性能开销

**并发处理**：
- goroutine 并发处理批量任务
- 提高批量处理效率

**缓存优化**：
- 缓存常用计算结果（如节气时刻）
- 减少重复计算

## 架构风险和应对

### 架构风险

| 风险 | 影响 | 应对策略 |
|-----|------|---------|
| 模块依赖变化 | 影响接口设计 | 接口隔离原则、依赖注入 |
| lunar-go API变化 | 影响 chronos 模块 | 桥接模式隔离 |
| 性能瓶颈 | 影响用户体验 | 性能优化、缓存优化 |
| 模块职责不清 | 影响开发和维护 | 单一职责原则、职责明确 |

---

### 应对策略

1. **接口隔离原则**：
   - 每个模块提供最小接口
   - 避免接口污染
   
2. **依赖注入模式**：
   - 通过接口注入依赖
   - 易于替换实现
   
3. **桥接模式隔离**：
   - chronos 使用桥接模式隔离 lunar-go
   - 避免 lunar-go API变化影响
   
4. **单一职责原则**：
   - 每个模块只有一个职责
   - 职责明确，易于理解
